# Университетский киноклуб — техническая спецификация

Документ предназначен для реализации. Все решения ниже согласованы; разделы, помеченные `TBA`, реализовывать не нужно, но структура данных должна допускать их добавление без миграции ломающего типа.

---

## 1. Суть системы

Студенты отмечают фильмы, которые хотели бы посмотреть. Раз в неделю система (или администратор) отбирает несколько фильмов, собирает информацию о свободном времени желающих, назначает показы, собирает подтверждения, проводит сеансы и фиксирует посещение с оценками.

Цикл состоит из четырёх этапов и повторяется еженедельно.

---

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **Желаемое** (`WISHLIST`) | Бессрочная отметка «хочу посмотреть», малый вес, медленное затухание |
| **Ближайшее** (`SOON`) | Отметка «готов посмотреть в ближайшие 2 недели», большой вес, автоматически сгорает |
| **Вес фильма** | Сумма весов всех активных отметок на момент расчёта |
| **Шорт-лист** | Набор фильмов, отобранных на этапе 1 для голосования по слотам |
| **Слот** | Интервал времени в конкретном зале, в который можно назначить показ |
| **Показ** (`Screening`) | Фильм, назначенный на конкретный слот |
| **Цикл** (`Round`) | Одна итерация: от среза этапа 1 до последнего показа недели |
| **Кворум** | Минимальное число подтверждений, при котором показ имеет смысл проводить |

---

## 3. Временная схема цикла

Все моменты времени в БД хранятся в **UTC**. Отображение — в локальной зоне вуза. Все указанные ниже времена — параметры, редактируемые главным администратором, а не константы в коде.

Пример для недели показов 8–14 сентября:

| Момент | Событие |
|---|---|
| постоянно | **Этап 1** активен: пользователи ставят и снимают отметки |
| ср 20:00 | Срез этапа 1. Формируются два рейтинга, уведомление админам |
| ср 20:00 → чт 08:00 | Окно администратора: правка шорт-листа, добавление своих фильмов |
| чт 08:00 | Автопилот, если шорт-лист не подтверждён. Публикация шорт-листа |
| чт 08:00 → сб 20:00 | **Этап 2**: выбор фильмов из шорт-листа + отметка свободных вечеров |
| сб 20:00 | Срез этапа 2. Админу доступна матрица «фильм × слот» |
| сб 20:00 → вс 18:00 | Окно администратора: расстановка показов |
| вс 18:00 | Автопилот, если расписание не подтверждено |
| вс 20:00 | Публикация расписания. **Этап 3**: сбор подтверждений |
| пн–вс | Показы. **Этап 4** после каждого |

Правила:
- Незанятые фильмы из шорт-листа после закрытия окна администратора **возвращаются в общий пул** без каких-либо пометок.
- Если все вечера недели заблокированы, этап 2 не запускается, публикуется сообщение «на следующей неделе показов не будет».
- Показ в понедельник допустим, но между публикацией и сеансом менее суток; при автопилоте понедельник использовать в последнюю очередь.

## 4. Этап 1 — интерес

### Две кнопки

| | `WISHLIST` | `SOON` |
|---|---|---|
| Базовый вес | `wishlist_base_weight` (по умолчанию 1.0) | `soon_weight` (по умолчанию 3.0) |
| Затухание | экспоненциальное, период полураспада `wishlist_half_life_days` (180) | нет |
| Нижний порог веса | `wishlist_weight_floor` (0.2) | — |
| Срок жизни | бессрочно | `soon_ttl_days` (14), затем снимается автоматически |
| Лимит на пользователя | нет | `soon_limit_per_user` (10) |

Кнопки независимы: можно поставить обе, тогда веса складываются.

### Формула веса

```
wishlist_weight(t) = max(
    wishlist_weight_floor,
    wishlist_base_weight * 0.5 ** (days_since(created_at) / wishlist_half_life_days)
)

soon_weight(t) = soon_weight  if days_since(created_at) <= soon_ttl_days else 0

film_weight = Σ по всем активным отметкам
```

**Критично:** вес нигде не хранится вычисленным. В БД лежат сырые события (`user_id`, `film_id`, `kind`, `created_at`, `revoked_at`), вес считается при чтении по текущим коэффициентам. Иначе изменение периода полураспада не пересчитает историю. Кэшировать можно, но с инвалидацией при изменении любого параметра весов.

### Снятие отметок

Обе отметки снимаются автоматически и одновременно в момент, когда пользователь **отмечен как посмотревший** фильм (этап 4). Фильм переходит в его раздел «Просмотренные». У тех, кто не пришёл, отметки не трогаются.

### Истечение `SOON`

Когда отметка сгорает, пользователю уходит уведомление: фильм не был выбран за 2 недели, готов ли посмотреть в ближайшие две. Кнопка «Продлить» ставит новую отметку `SOON` с текущей датой.

### Предложение фильма

У любого пользователя есть кнопка «Не нашёл фильм». Заявка (название, год, ссылка — опционально) уходит администраторам в очередь модерации. Админ добавляет фильм в БД вручную или отклоняет заявку с комментарием. Автора заявки уведомляют о результате.

## 5. Отбор шорт-листа (переход 1 → 2)

### Что видит администратор в среду

Два независимых рейтинга по одним и тем же данным:

1. **По весу** — простая сортировка `film_weight` по убыванию.
2. **По покрытию аудитории** — жадный алгоритм:
   - шаг 1: фильм с максимальным весом;
   - шаг N: фильм с максимальным весом, считая только тех пользователей, чьи отметки ещё не «покрыты» ни одним выбранным фильмом;
   - повторять до `shortlist_size` (по умолчанию 5).

По каждому фильму в списке администратору показываются: вес, число отметок каждого типа, внешний рейтинг (TMDB/КП), внутренний рейтинг вуза с числом оценок, число пользователей, держащих отметку дольше `long_wait_days` (флаг «давно ждут»), и, если фильм уже показывали — история показов с датами, ожидаемой и фактической явкой.

Администратор формирует финальный шорт-лист: берёт из любого списка, убирает, добавляет любой фильм из базы по своему усмотрению. Проверка допустимости контента (возрастные ограничения, уместность) — зона ответственности администратора, автоматических фильтров нет.

### Автопилот

Срабатывает в `stage1_autopilot_at`, если шорт-лист не подтверждён вручную. Использует рейтинг по покрытию, отбрасывая фильмы с весом ниже `min_weight_threshold`. Если прошедших порог меньше `shortlist_size`, берёт сколько есть и помечает цикл флагом «низкая активность». Админам уходит уведомление о том, что выбор сделан автоматически, с возможностью правки до публикации.

Автопилот считает своё решение **всегда**, даже когда админ работает вручную, и показывает его рядом как подсказку.

## 6. Этап 2 — фильмы и время

Пользователь видит шорт-лист и делает два независимых действия:

1. Отмечает **все** фильмы шорт-листа, на которые пошёл бы (множественный выбор, не ранжирование).
2. Отмечает **все** вечера недели, в которые свободен (множественный выбор).

Голос за фильм без указания хотя бы одного свободного вечера бесполезен — предупредить в интерфейсе.

### Что видит администратор в субботу

Матрица `фильм × слот`, в каждой ячейке — число пользователей, которые одновременно выбрали этот фильм и свободны в этот слот. Плюс маргинальные суммы: популярность каждого фильма и загруженность каждого вечера.

Администратор расставляет показы вручную, соблюдая: один показ на слот, один фильм не более одного раза за цикл, заблокированные вечера недоступны.

### Автопилот

Задача о назначениях. Матрица стоимостей `C[фильм][слот]` = ожидаемая явка. Решение — `scipy.optimize.linear_sum_assignment` (максимизация). Слоты, где ожидаемая явка ниже `min_attendance`, не назначаются вовсе. При равенстве стоимостей приоритет отдаётся фильму, дольше находящемуся в шорт-листах без показа.

## 7. Этап 3 — подтверждения

После публикации расписания все, кто голосовал за назначенный фильм, получают уведомление и кнопку «Приду».

- Ограничений на число подтверждений одного человека нет: можно подтвердиться хоть на все сеансы недели.
- Есть кнопка «Не смогу». Отмена в последние `late_cancel_hours` (24) часа перед показом фиксируется в статистике и вызывает предупреждение пользователю («так делать не стоит, отменяйте заранее»). Санкций нет.
- Подтверждения ограничены `hall_capacity`. При переполнении — лист ожидания в порядке подтверждения, при освобождении места автоматическое уведомление первому в очереди.
- Если число подтверждений за `early_warning_hours` до показа меньше `min_attendance`, администраторам уходит предупреждение. Решение о проведении или отмене принимает администратор — автоматической отмены нет.

### Напоминания

За 24 часа и за 2 часа до показа всем подтвердившим.

### Правки расписания администратором

Разрешены после публикации: перенос в другой слот, отмена, замена фильма, смена зала, смена времени начала.

- Изменение **времени или даты** → все подтверждения сбрасываются, запрашиваются заново (доступность привязана к конкретному окну).
- Изменение **зала** → подтверждения сохраняются.
- Отмена требует обязательного комментария, который уходит в уведомлении.
- Каждая правка пишется в журнал изменений: кто, что, когда, комментарий.
- Уведомления получают **только затронутые пользователи**.

## 8. Этап 4 — посещение и обратная связь

### Фиксация присутствия

Два равнозначных пути:

1. **QR-код** на экране в зале → страница сеанса → вход в аккаунт → отметка + форма.
2. **Цифровой код** в Telegram-боте: пользователь вводит код, показанный на экране.

Общий контур защиты (код легко переслать, поэтому):

- код действителен только в окне `[начало сеанса, начало + attendance_window_minutes]` (по умолчанию 20 минут);
- код ротируется каждые `code_rotation_seconds` (60), на экране отображается актуальный (схема, аналогичная TOTP);
- принимается только от пользователей, подтвердивших приход на этапе 3;
- модератор видит живой список отметившихся и может **добавить пользователя вручную**.

### Обратная связь

Открывается сразу после отметки присутствия.

- Оценка фильма — **обязательна**? Нет: обязательна только отметка присутствия. Форма опциональна.
- Не заполнившим сразу — напоминание через `feedback_reminder_hours` (24).

Содержание формы:
- оценка фильма, 10 баллов;
- текстовый отзыв (опционально);
- оценка организации отдельным полем: звук, изображение, зал, время (опционально).

Оценка организации **не** входит в рейтинг фильма — иначе плохая проекция утопит хорошее кино.

### Последствия

Для отметившегося: обе отметки сняты, фильм в «Просмотренных», оценка в общем рейтинге вуза.
Для неявившегося после подтверждения: факт неявки в статистике, уведомление с просьбой в будущем отменять заранее. Отметки не снимаются.

### Повторные показы

Кулдаунов нет. Фильм может быть выбран снова в любой момент — его вес естественно падает на тех, кто уже посмотрел, и сохраняется у тех, кто не смог прийти. Администратору при отборе показывается история прошлых показов.

## 9. Роли и права

| Действие | Главный админ | Админ | Модератор |
|---|---|---|---|
| Параметры системы (веса, полураспад, дедлайны, вместимость, кворум) | ✓ | — | — |
| Назначение ролей | админов и модераторов | модераторов | — |
| Закрытие этапа 1, формирование шорт-листа | ✓ | ✓ | ✓ (если этап не закрыт вовремя) |
| Закрытие этапа 2, расстановка показов | ✓ | ✓ | ✓ (если этап не закрыт вовремя) |
| Правка опубликованного расписания | ✓ | ✓ | — |
| Блокировка вечеров | ✓ | ✓ | — |
| Отмена сеанса | ✓ | ✓ | только с подтверждением админа |
| Проведение сеанса: код, ручные отметки | ✓ | ✓ | ✓ |
| Модерация заявок на добавление фильмов | ✓ | ✓ | — |
| Полная аналитика | ✓ | ✓ | — |

Запрос модератора на отмену: создаётся заявка, всем админам уходит уведомление, отмена происходит только после подтверждения любого из них. До подтверждения сеанс считается активным.

## 10. Слоты и залы

Текущая конфигурация: **один зал**, семь фиксированных вечеров, сбор в 19:00, не более одного показа в вечер.

Модель данных обязана описывать слот как `(зал, дата, время начала, длительность)`, даже если сейчас все значения фиксированы. Это позволит без переписывания перейти к:
- нескольким залам;
- сетке блоков по 2,5–3 часа с тепловой картой свободного времени (`TBA`);
- нескольким показам в один вечер.

Администратор может пометить любой вечер как заблокированный (пары, мероприятие, праздник). Автопилот заблокированные вечера не использует.

## 11. Каталог фильмов

### Источники

**TMDB — основа.**
- Первичный импорт: ежедневный экспорт всех ID (`files.tmdb.org/p/exports/movie_ids_*.json.gz`), фильтр `vote_count >= 100` + непустая дата выхода → примерно 40–60 тыс. фильмов.
- По каждому ID: `GET /movie/{id}?language=ru-RU&append_to_response=videos` → русское название, оригинальное название, описание, `poster_path`, жанры, длительность, год, ключ трейлера на YouTube, `vote_average`, `vote_count`.
- Rate limit ~20 rps, полный проход около часа.
- **Постеры не хранить.** Сохраняется только `poster_path`, URL собирается на лету с CDN TMDB.
- Обновление: ночной крон по `/movie/changes` (изменившиеся за сутки) + еженедельный `/discover` по дате выхода для новинок.
- Лицензия CC BY-NC. Требуется видимая атрибуция TMDB на страницах с их данными.

**Кинопоиск — ленивая подгрузка.**
- Официального API нет; `kinopoisk.dev` со связкой по `externalId.tmdb`.
- Не тянуть для всего каталога. Запрашивать только для фильмов, которые кто-то отметил или чью карточку открыли. Кэш на 30 дней. Так бесплатный лимит не превышается.

**Letterboxd не использовать** — публичного API нет, скрейпинг запрещён их правилами. Ориентироваться на UX можно, брать данные нельзя.

### Карточка фильма

Постер, название (ru + оригинал), год, длительность, жанры, описание, ссылка на трейлер, обе кнопки отметок, число желающих, внутренний рейтинг вуза с числом оценок, внешний рейтинг, отзывы студентов.

Три разных числа на карточке не смешивать: внешний рейтинг, внутренний рейтинг, счётчик желающих. Внутренний рейтинг первые месяцы будет основан на единицах оценок — показывать с явной пометкой числа оценивших, при `< 5` оценок не показывать вовсе.

**Не показывать публично:** поимённый список желающих; факт нахождения фильма в текущем шорт-листе.

Сортировка каталога по умолчанию — **не** по популярности (эффект присоединения к большинству убивает хвост). Сортировка по популярности доступна явным выбором.

## 12. Аккаунты и вход

Один аккаунт, два способа входа: Telegram и веб.

- При регистрации через веб привязка Telegram **обязательна сразу**, до доступа к функциям. Все уведомления идут только в Telegram.
- Веб-вход: SSO/ЛК вуза, если доступно; иначе magic-link на университетскую почту.
- Telegram-вход: авторизация через `initData` Mini App.
- Один Telegram-аккаунт = один аккаунт в системе.

Гости не из вуза: `TBA`, сейчас не поддерживаются.

## 13. Параметры, редактируемые главным администратором

Все в интерфейсе, без деплоя:

**Веса**
- `wishlist_base_weight`, `wishlist_half_life_days`, `wishlist_weight_floor`
- `soon_weight`, `soon_ttl_days`, `soon_limit_per_user`

**Зал и явка**
- `hall_capacity`
- `min_attendance` (кворум)
- `early_warning_hours`, `late_cancel_hours`

**Цикл**
- `shortlist_size`, `min_weight_threshold`, `long_wait_days`
- все дедлайны этапов и времена напоминаний
- тумблеры автопилота отдельно для этапа 1 и этапа 2

**Присутствие**
- `attendance_window_minutes`, `code_rotation_seconds`, `feedback_reminder_hours`

Требование к интерфейсу весов: **песочница**. Админ двигает ползунок и сразу видит, как переставляется текущий рейтинг, до применения изменений. Реализуемо бесплатно, поскольку веса считаются при чтении.

## 14. Аналитика

Доступна главному администратору и администраторам.

**Воронка по неделям:** отметил интерес → проголосовал на этапе 2 → подтвердил приход → пришёл. Каждый переход диагностирует свою проблему: провал между этапом 2 и подтверждением — неудобные слоты; провал между подтверждением и явкой — подтверждение не воспринимается всерьёз, усиливать напоминания.

**Прочее:** динамика активной аудитории, средняя явка, доля отменённых сеансов, распределение явки по дням недели, доля заполнения зала, статистика неявок по пользователям, топ фильмов по «давно ждут».

## 15. Модель данных

Ориентир, не догма. Postgres.

```
users              id, tg_id, email, display_name, role, created_at, tz
                   role ∈ {user, moderator, admin, superadmin}

films              id, tmdb_id, kp_id, title_ru, title_orig, year, runtime_min,
                   overview, poster_path, trailer_key, genres[],
                   ext_rating, ext_votes, status, added_by, created_at
                   status ∈ {active, hidden, pending_moderation}

film_requests      id, user_id, raw_title, raw_year, note, status,
                   resolved_film_id, resolved_by, created_at
                   status ∈ {pending, approved, rejected}

interests          id, user_id, film_id, kind, created_at, revoked_at, revoke_reason
                   kind ∈ {wishlist, soon}
                   revoke_reason ∈ {manual, expired, watched}
                   -- НИКОГДА не хранит вычисленный вес

rounds             id, week_start, stage, shortlist_locked_at, schedule_locked_at,
                   low_activity, created_at
                   stage ∈ {collecting, shortlist_review, slot_voting,
                            schedule_review, published, running, closed}

shortlist_items    id, round_id, film_id, source, position
                   source ∈ {auto_weight, auto_coverage, admin}

slots              id, round_id, hall_id, starts_at (UTC), duration_min,
                   blocked, blocked_reason

halls              id, name, capacity, active

film_votes         id, round_id, user_id, film_id, created_at
availability       id, round_id, user_id, slot_id, created_at

screenings         id, round_id, film_id, slot_id, status, expected_attendance,
                   decided_by, decided_at, cancel_reason
                   status ∈ {scheduled, cancelled, completed}

confirmations      id, screening_id, user_id, state, created_at, cancelled_at
                   state ∈ {confirmed, waitlist, cancelled}

attendance         id, screening_id, user_id, method, marked_at, marked_by
                   method ∈ {qr, code, manual}

feedback           id, screening_id, user_id, film_rating, review_text,
                   visit_rating, discussion_rating, discussion_skip, created_at
                   discussion_skip ∈ {absent, unsure}  — опрос CSAT после показа

settings           key, value, updated_by, updated_at
audit_log          id, actor_id, entity, entity_id, action, payload, created_at
notifications      id, user_id, kind, payload, sent_at, read_at
```

Индексы под частые запросы: `interests(film_id, revoked_at)`, `interests(user_id, revoked_at)`, `availability(round_id, slot_id)`, `film_votes(round_id, film_id)`.

## 16. Состояния

**Отметка (`interest`):**
`active` → `revoked_manual` | `revoked_expired` (только `soon`) | `revoked_watched`

**Фильм для конкретного пользователя:**
`не отмечен` → `в желаемом` / `в ближайших` (независимо, комбинируются) → `просмотрен`

**Цикл (`round`):**
`collecting` → `shortlist_review` → `slot_voting` → `schedule_review` → `published` → `running` → `closed`

**Показ (`screening`):**
`scheduled` → `completed` | `cancelled`

## 17. Технологический стек (рекомендация)

- **Backend:** Python + FastAPI, Postgres, SQLAlchemy + Alembic.
- **Бот:** aiogram 3, Telegram Mini App для интерфейса выбора слотов и карточек.
- **Планировщик:** APScheduler или Celery beat (в итоге — ни то, ни другое: фоновые циклы бота, см. `backend/app/bot/loops.py`). Задачи: срез этапа 1, автопилот 1, срез этапа 2, автопилот 2, публикация, напоминания 24ч/2ч, истечение `soon`, напоминание об обратной связи, ночной импорт TMDB.
- **Веб:** любой SPA-фреймворк, авторизация через SSO вуза + обязательная привязка TG.
- **Назначения:** `scipy.optimize.linear_sum_assignment`.

Все фоновые задачи должны быть идемпотентны: повторный запуск не должен приводить к двойной публикации или дублю уведомлений.
